# 뉴스 알림 설계 (3단계)

`2026-09-20` · 선행 문서: [`2026-09-19-realtime-disclosure-alert-design.md`](2026-09-19-realtime-disclosure-alert-design.md)

## 1. 목표

시장에 영향을 주는 뉴스를 선별해 텔레그램으로 전달한다. 1단계에서 만든 중복제거·발송·재시도·감시 인프라를 그대로 쓴다.

## 2. 가치 제안이 DART와 다르다

이것을 먼저 못 박는다. 뒤따르는 설계 대부분이 여기서 나온다.

DART는 원천 API를 직접 때린다 — 공시가 접수되면 우리가 바로 본다. 뉴스는 **기자가 쓰고 → 데스크를 거쳐 → 발행되고 → 배포 채널에 반영되는** 사슬이 있고, 그중 마지막 한 칸을 제외하면 우리가 줄일 수 없다.

| | DART | 뉴스 |
|---|---|---|
| 가치 | **가장 먼저 안다** | **20개 매체를 대신 지켜본다** |
| 경쟁 우위 | 지연 시간 | 누락 없음 + 노이즈 제거 |

뉴스에서 "가장 먼저"를 약속하지 않는다. 구조적으로 지킬 수 없는 약속이다. §4.2 의 실측이 이를 뒷받침한다 — 발행에서 RSS 반영까지 중앙값 3.5분이고, `[속보] 합참 "북한, 동해상으로 미상 발사체 추가 발사"` 는 **7.8분** 걸렸다. 매크로 트랙이 잡아야 할 바로 그런 이벤트가 가장 느렸고, 폴링을 아무리 조여도 줄지 않는 시간이다. 대신 사용자가 실제로 못 하는 일 — 20개 매체를 동시에 지켜보며 노이즈를 걸러내는 일 — 을 한다.

## 3. 두 개의 트랙

종목에 연결되는 뉴스와 그렇지 않은 뉴스는 필터가 완전히 다르다. 같은 파이프라인에 태우되 룰셋을 나눈다.

| | 종목 트랙 | 매크로 트랙 |
|---|---|---|
| 1차 게이트 | 상장사명 매칭 | 주체 + 행위 **조합** |
| 예시 | "한미약품, 기술수출 계약" | "트럼프 + 관세", "연준 + 금리", "이스라엘 + 공습" |
| 클러스터링 | 강한 키워드면 **건너뜀** | **필수** (매체 3곳 이상) |
| 발송 지연 | 즉시 | 2~3분 |
| 빈도 상한 | 없음 | **시간당 3건** (3c에서 튜닝) |

**매크로에서 클러스터링을 필수로 두는 이유는 두 가지다.** 하나는 `"트럼프"` 단독 매칭이 하루 수백 건의 정치 가십을 끌어오기 때문이고 — 그래서 인물명이 아니라 주체+행위 조합으로 간다 — 다른 하나는 **매크로는 늦어도 손해가 작기** 때문이다. 개별 종목 수주 뉴스는 1분이 승부지만 관세 발표는 시장 전체가 반응하는 데 시간이 걸려 3분 지연의 비용이 훨씬 낮다. 종목 트랙에서 포기할 수 없는 속도를 매크로에서는 정확도와 바꾼다.

**빈도 상한이 없으면 채널이 죽는다.** 매크로 뉴스는 하루 종일 쏟아지고, 상한이 없으면 정작 중요한 종목 알림이 묻힌다. 시작값은 시간당 3건으로 잡되, 상한에 걸려 버려진 건수를 기록해 3c에서 조정한다 — **버린 것을 세지 않으면 상한이 적절한지 알 수 없다.**

## 4. 소스

### 4.1 경로 선택

| | 속도 | 합법성 | 누락 위험 |
|---|---|---|---|
| **RSS 직접** (채택) | 중 | 배포 의도로 공개된 피드 | **낮음** — 전체 피드 |
| 네이버 뉴스 검색 API (보조) | 중~하 | 공식 API | **높음** — 쿼리한 것만 |
| 직접 크롤링 (배제) | 상 | robots.txt·약관 위반 소지 | 낮음 |

**RSS를 주력으로 한다.** 전체 피드를 주므로 누락이 구조적으로 없고, 이것이 §2의 가치 제안과 직결된다.

**네이버 검색 API의 치명적 약점은 속도가 아니라 누락이다.** 검색 API는 던진 쿼리에만 답한다. 상장사 2,800개를 다 검색할 수 없으니 **무엇을 검색할지 이미 알아야** 하는데, 우리가 하려는 건 정확히 그 반대다. 다만 **매크로 트랙은 감시할 키워드가 애초에 정해져 있어**(관세·금리·전쟁) 이 약점이 약점이 아니므로, 매크로 보강용 보조 소스로 쓴다.

**직접 크롤링은 배제한다.** 속도를 조금 얻자고 서비스 전체를 법적 위험에 두는 거래다. 유료화 계획이 있으면 더욱 그렇다.

### 4.2 실측 (2026-09-20 일요일 저녁)

12개 후보 피드 중 9개가 200을 반환했다. RSS는 살아 있다.

| 매체 | 발행 간격 | 조건부 요청 | `description` | Node 도달 |
|---|---|---|---|---|
| 연합뉴스 시장 | 촘촘 (120건) | ETag | 68자 | ✅ |
| 연합뉴스 속보 | 1.2분 | ETag + Last-Modified | 83자 | ✅ |
| 머니투데이 | 1.2분 | ETag + Last-Modified | **699자** | ✅ |
| 조선비즈 증권 | 느림 (22건) | ETag | 36자 | ✅ |
| 한국경제 증권 | 33분 | Last-Modified | **없음** | ✅ |
| 매일경제 증권 | 24분 | 없음 | 102자 | ✅ |
| 아시아경제 | 34분 | 없음 | 302자 | ✅ |
| **이데일리** | 촘촘 | ETag + Last-Modified | 203자 | ❌ **TLS 1.0 전용** |

> **측정 오류 정정 (2026-09-20).** 최초 스파이크가 SSL 인증서 검증을 끈 채로 돌았고, 그 때문에 이데일리가 정상 피드로 잡혔다. 실제로는 `rss.edaily.co.kr` 이 **TLS 1.0 으로만 협상**하며(curl 도 TLSv1.0 으로 붙는다) Node 의 기본 최소 버전이 TLS 1.2 라 워커에서 `ERR_SSL_UNSUPPORTED_PROTOCOL` 로 실패한다. `www.edaily.co.kr` 은 TLS 1.2 를 쓰지만 RSS 경로가 전부 soft-404(200 인데 item 0건)다.
>
> **TLS 하한을 낮추지 않는다.** 피드 하나를 얻자고 워커 전체의 TLS 바닥을 폐기된 프로토콜(RFC 8996)까지 내리는 거래다. 이데일리를 목록에서 뺀다.
>
> 지연 중앙값은 영향받지 않는다 — 이데일리 23건을 빼도 남은 11건의 중앙값이 그대로 3.5분이다.

일요일 저녁 기준이므로 평일 장중 빈도는 이보다 높다.

**발행(`pubDate`) → RSS 반영 지연** — 20분간 60초 주기로 폴링해 새로 나타난 기사 34건을 관측했다.

| 피드 | 관측 | 중앙값 | 최소 | 최대 |
|---|---|---|---|---|
| 머니투데이 | 4 | **1.1분** | 0.8분 | 1.3분 |
| 이데일리 | 23 | 3.6분 | 0.5분 | 6.1분 |
| 연합뉴스 속보 | 7 | **5.1분** | 3.3분 | **7.8분** |
| 전체 | 34 | **3.5분** | 0.5분 | 7.8분 |

> 측정의 한계: 폴링이 60초 주기였으므로 관측값은 실제 지연에 최대 60초의 자체 지연을 포함한다. 실제 지연은 이보다 0~1분 작다. 또한 `pubDate` 가 최초 발행 시각인지 최종 수정 시각인지는 매체마다 다를 수 있다. 일요일 저녁 표본이라 평일 장중에 재측정이 필요하다.

### 4.3 실측이 설계에 강제한 것

**`description`은 필터에만 쓰고 발송하지 않는다.** 머니투데이가 699자를 주는데 이는 본문 상당 부분이다. 그대로 재배포하면 저작권 문제가 실제로 발생한다. 반대로 필터 정확도에는 결정적이다 — 제목만으로는 "삼성전자, 3분기 실적 발표"가 호실적인지 어닝쇼크인지 알 수 없다. **받아서 판정에 쓰고, 나가는 메시지에는 제목 + 링크 + 자체 요약만 담는다.** 한국경제처럼 `description`이 없는 매체는 제목만으로 판정하므로 정확도가 낮다.

**`pubDate`를 신뢰하지 않는다.** 매일경제가 534분 후의 미래 시각을 반환했다. 발송 판단은 `firstSeenAt`으로 한다. `events` 테이블이 이미 `occurredAt`(nullable)과 `firstSeenAt`(notNull)을 분리해 들고 있어 구조 변경이 필요 없다. DART의 게이트 8에서 얻은 교훈과 같은 것이다.

**클러스터에서 매체를 단순히 세지 않는다.** 연합은 통신사라 1차 소스이고, 같은 사건을 연합이 쓴 것과 재인용 매체가 쓴 것은 무게가 다르다.

**다만 권위와 속도가 일치하지 않는다.** 실측에서 연합 속보 피드의 RSS 반영이 가장 느렸다(중앙값 5.1분, 최대 7.8분). 1차 소스인데 우리에게는 가장 늦게 도착한다. 클러스터 가중치는 권위로 매기고, 발송 시점은 가장 먼저 도착한 매체를 기준으로 삼는다.

**폴링 주기를 30초보다 짧게 하지 않는다.** RSS 반영 지연이 중앙값 3.5분인데 그 앞에서 폴링 주기는 반올림 오차다. 짧게 잡아도 얻는 것이 없고 상대 서버 부담만 는다. 조건부 요청(ETag/Last-Modified) 지원 매체는 30초, 미지원 매체는 2~3분으로 나눈다 — 미지원 매체를 짧게 폴링하면 매번 피드 전문을 받게 된다.

이것이 DART 와의 중요한 차이다. DART 는 우리 폴링 주기가 곧 지연이지만, 뉴스는 지연의 대부분이 우리 바깥에 있다.

## 5. 필터

### 5.1 종목 연결

뉴스 제목과 `description`에서 상장사명을 매칭한다. DART의 `stock_code` 게이트와 같은 역할이다.

**실측 — 4주치 공시에 등장한 상장사 1,895개 중 오탐 위험이 있는 이름은 55개(2.9%)다.**

| 유형 | 개수 | 예 |
|---|---|---|
| 일반 단어와 동일 | 29 | 대상, 한창, 노을, 동양, 남성, 전방, 진도, 레이, 캐리 |
| 흔한 사람 이름 | 10 | 성우, 진영, 우진, 유신, 태성, 덕성, 서한 |
| 2글자 영문 약어 | 16 | CJ, DB, LG, SK, NC, LS, GS, E1 |

나머지 1,840개는 이름만으로 안전하게 매칭된다. **55개만 예외 규칙을 붙이면 되므로 이 관문은 생각보다 싸다.**

예외 처리 방식: 해당 이름은 단독 매칭을 인정하지 않고, **종목 문맥 신호**(주가·증시·상장·공시·실적·거래량 등)가 같은 문장에 있을 때만 통과시킨다.

> 측정의 한계: 1,895개는 4주 안에 공시를 낸 회사만이라 전체 상장사(~2,800개)의 일부다. "일반 단어" 분류는 사전 대조가 아니라 사람 판단으로 골랐다. 3a 운영 데이터로 재측정한다.

### 5.2 영향 키워드

DART 키워드셋을 상당 부분 재활용한다. **사건의 종류(수주·임상·인수·횡령)는 공시든 뉴스든 같다.** 이것이 뉴스를 붙일 때 가장 큰 자산이다.

다만 뉴스 제목은 자유 형식이라 DART의 정형 제목 매칭을 그대로 쓸 수 없다. 표현 변형(`수주` / `계약 체결` / `공급 계약`)을 흡수해야 한다.

### 5.3 중복 제거와 클러스터링

뉴스에는 `rcept_no` 같은 자연 멱등키가 없다. 같은 사건을 20개 매체가 쓴다.

- **멱등키**: RSS `guid`(없으면 링크). 같은 기사의 재수신을 막는다.
- **클러스터**: 같은 종목·사건을 시간 창 안에서 묶는다. 서로 다른 기사이므로 멱등키로는 안 잡힌다.

**이 약점이 동시에 무기다.** 여러 매체가 동시에 썼다는 것 자체가 언론사들이 대신 해준 중요도 판정이다.

## 6. 저장

### 6.1 이미 지원되는 것

`runIngest`는 verdict와 무관하게 모든 이벤트를 `recordEvent`로 저장한다. `events` 테이블이 `verdict`·`tier`·`rule`·`raw`를 들고 있다. **"전량 수집 + 확신하는 것만 발송"은 구조적으로 이미 지원되며, 뉴스 소스를 붙이면 자동으로 따라온다.**

### 6.2 저장량 — 보관 정책이 필수다

DART 공시 1건 실측: `raw` 273B, 행 전체 675B.

| 시나리오 | 1년 후 | 500MB 대비 |
|---|---|---|
| 현재 (DART만, 보관 정책 없음) | 181MB | 36% |
| 뉴스 추가, 보관 정책 없음 | **742MB** | **148%** ❌ |
| 뉴스 추가 + `raw` 축소 + 90일 보관 | 183MB | 37% ✅ |

**대응:**

1. **뉴스의 `raw`를 축소한다** — 제목·링크·매체·시각만(~500B). 원문 `description`은 판정에 쓰고 저장하지 않는다. 저작권 관점에서도 이쪽이 낫다.
2. **90일 보관** — 그 이상 지난 `events`와 종결된 `outbox` 행을 삭제한다.
3. **주 1회 덤프 백업** — `events`를 압축해 보관한다.

### 6.3 삭제 로직이 지금 없다

`events`도 `outbox`도 영원히 쌓인다. 발송 완료된 `sent` 행과 `dead` 행이 그대로 남아, 스키마 주석이 경고한 *"sent/dead가 쌓일수록 순차 스캔 비용이 매 폴링 사이클에 얹힌다"* 가 실제로 진행 중이다. **뉴스와 무관하게 이미 필요한 작업이다.**

### 6.4 백업이 필요한 이유 — 뉴스에만 있는 비대칭

- **DART는 다시 모을 수 있다.** API가 과거 공시를 보관하므로 DB가 날아가도 재수집이 가능하다. 최초 15,477건을 실제로 그렇게 모았다.
- **뉴스는 못 모은다.** RSS와 뉴스 API는 최근 것만 준다. 게다가 **우리가 내린 판정(`verdict`/`rule`)은 어디에도 없어** 지나간 기사에 대해 재구성이 불가능하다.

**뉴스를 붙이는 순간 DB가 유일본인 데이터가 생긴다.** 무료 티어에 자동 백업이 없다는 점이 여기서 문제가 된다. 튜닝 데이터는 이 프로젝트에서 가장 값비싼 자산이다 — DART 필터를 27.9건/일에서 58.1건/일로 만든 것이 그 데이터 분석이었다.

## 7. 규제와 저작권

1단계의 제약이 그대로 적용되며, 매크로 트랙에서 더 민감하다.

| 항목 | 경계 |
|---|---|
| 유사투자자문 | 호재/악재 판정, 목표가, 매매의견을 **생성하지 않는다** |
| 영향 판정 | **고르는 데만 쓰고 메시지에 표시하지 않는다** |
| 매크로 해석 | "관세 → 반도체주 영향" 같은 연결을 **쓰지 않는다.** 어느 종목·업종에 영향인지 적지 않는다 |
| 저작권 | 제목 + 링크 + 자체 요약만. `description` 원문을 발송하지 않는다 |

## 8. 단계

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| **3a** | RSS 어댑터 + 종목 트랙 + 전량 저장 | 발송과 동시에 튜닝 데이터가 쌓이기 시작한다 |
| **3b** | 90일 보관 + 덤프 백업 + `outbox` 정리 | 저장량이 평형에 든다 |
| **3c** | 클러스터링 + 매크로 트랙 | 3a 데이터로 클러스터 임계값을 정한 뒤 |
| **3d** | 주가 라벨링 배치 + 필터 튜닝 | 2주치 데이터 확보 후 |

**3b를 3c보다 앞에 두는 이유**는 보관 정책 없이 뉴스를 쌓으면 1년에 742MB로 무료 티어를 넘기기 때문이다. 카운트다운은 3a가 켜지는 순간 시작된다.

**주가 라벨링(3d)은 발송 파이프라인과 분리한다.** 하루 1회 일별 시세를 받아 `events`에 등락률을 채우는 배치이며, 실시간 워커 루프에 넣지 않는다.

**구현 계획은 3a + 3b 까지만 작성한다.** 3c 의 클러스터 임계값과 3d 의 라벨링 기준은 3a 운영 데이터가 있어야 정할 수 있어, 지금 계획을 쓰면 근거 없는 숫자를 박게 된다. 1단계에서 필터를 실제 공시 15,477건으로 튜닝한 것과 같은 순서다.
